# Contributing to setup-grimoire

## What's here

| Path | Purpose |
|------|---------|
| `action.yml` | The composite GitHub Action that installs `grim` |
| `.github/scripts/install.sh` | The Linux/macOS install step — the action calls it, tests drive it |
| `.github/scripts/install.ps1` | The Windows install step |
| `tests/install/` | bats suites for `install.sh`, Pester suites for `install.ps1` |
| `external/` | Vendored `bats-core`, `bats-support`, `bats-assert` (git submodules) |
| `Taskfile.yml` | Every lint and test command CI runs |
| `site/` | Static site behind `setup.grimoire.rs` — shell/PowerShell installers and the landing page, deployed via GitHub Pages |
| `.github/workflows/test.yml` | Lint, bats, Pester and the 3-OS smoke test; DCO sign-off on pull requests |
| `.github/workflows/release.yml` | Runs the suite against a pushed tag, moves `v1`, publishes the release |
| `.github/workflows/pages.yml` | Deploys `site/` to GitHub Pages on push to `main` |
| `.github/scripts/dco.sh` | The DCO check, runnable locally — see [License](#license) |

There's no compiler here — no Rust, no package manifest. The action is a
`runs: using: composite` wrapper around two install scripts, and `site/`
is served as-is. `Taskfile.yml` is the entry point for everything else:

```sh
task lint    # shellcheck, shfmt, PSScriptAnalyzer, actionlint, annotation gate
task test    # bats + Pester
```

Both are what CI runs, so a green pair locally means a green pipeline.
`task lint` needs `shellcheck`, `shfmt`, `actionlint` and a `pwsh` with
PSScriptAnalyzer; `task test` needs `pwsh` with Pester 5, `python3`, and
the submodules (`task test:bootstrap`, or `git submodule update --init
--recursive`).

## Testing the action

`task test` is the fast loop. Both suites drive the real
`.github/scripts/install.{sh,ps1}` as child processes against a localhost
fixture server that serves a runtime-built grim release, so nothing is
mocked and the tested path is the shipped path. The runner environment
(`RUNNER_TEMP`, `GITHUB_PATH`, `GITHUB_OUTPUT`) is faked in `setup()`.

Two rules for new tests:

- Assert the **exact** `::error::` annotation text alongside the exit
  code. Those annotations are the action's user-facing contract, and
  `task lint:annotations` fails if any annotation in either script has no
  test asserting it.
- Fixture releases are built at runtime by `server_build_release` /
  `New-GrimFixture`. Do not check in archives.

`.github/workflows/test.yml`'s `smoke` job is still the end-to-end proof:
it runs `uses: ./` on ubuntu/macos/windows against the real GitHub
release. Push a branch or open a pull request to exercise it.

If you have [`act`](https://github.com/nektos/act) and Docker, you can run
the Linux leg of the smoke job locally.

## Releasing

Push a `vX.Y.Z` tag. `.github/workflows/release.yml` validates the tag,
runs the whole suite against the tagged tree, moves the `v1` pointer, then
publishes the release. There is no `CHANGELOG.md` by design — release
notes are generated by `gh release create --generate-notes`.

Try it first without publishing anything:

```sh
gh workflow run release.yml -f dry_run=true -f tag=v1.2.0
```

**If you ever loosen the trigger to include prereleases**, three things
have to change in the same commit: `v1.3.0-rc.1` derives major `v1`, so
the tag-move step must stay skipped for prerelease suffixes (it already
is — do not remove that `if:`), `gh release create` must get
`--prerelease` (it already does), and the recursion question has to be
re-answered. Today `v1` cannot retrigger the workflow because the tag
pattern is anchored and because pushes made with `GITHUB_TOKEN` do not
create workflow runs — and that second guard disappears silently if
anyone swaps in a PAT or an App token.

Publishing to the GitHub Marketplace is a manual, one-time opt-in on the
release page; nothing here automates it.

## Testing the installers

`site/sh` and `site/ps1` are thin bootstrap scripts that fetch and run the
real cargo-dist installer — keep them that way, don't grow install logic
here.

```sh
shellcheck site/sh .github/scripts/dco.sh
sh -n site/sh
```

`site/sh` is covered by `task lint:sh`. `site/ps1` has no local lint in
this repo's toolchain; if you have `pwsh`,
`pwsh -NoProfile -Command '$ErrorActionPreference = "Stop"; . { <paste> }'`
catches syntax errors. Otherwise review by eye.

`site/index.html` is a static page; open it in a browser to check rendering.

## Commit Conventions

This repo doesn't run a commit-lint job, but existing history follows
[Conventional Commits](https://www.conventionalcommits.org/) (`feat:`,
`fix:`, `chore:`, ...) — keep doing that.

## Branch Model

Branch from `main` — never commit directly to `main`. Keep commits atomic.

outbound, as Apache-2.0 §5 already presumes. Nothing you contribute is
relicensed, and you keep the copyright in your own work.

**There is no CLA.** Instead, sign off your commits under the
[Developer Certificate of Origin](https://developercertificate.org/) — a
one-line statement that you wrote the patch, or otherwise have the right to
submit it under this license:

```sh
git commit -s          # appends: Signed-off-by: Your Name <you@example.com>
```

The name and email must be real, and the sign-off address must match the one
that authored the commit. If you are contributing work owned by an employer,
make sure you have their permission before you sign off.

CI checks this on every pull request (existing history predates the DCO
requirement and is not checked retroactively). If you forget, `git rebase
--signoff main..HEAD` fixes the whole branch at once. Run the same check
CI runs yourself with:

```sh
.github/scripts/dco.sh              # checks main..HEAD
.github/scripts/dco.sh <range>      # or any explicit range
```

The copyright holder named in `LICENSE` is **The Grimoire Authors** — that
is every person with a commit in this repository, as listed by:

```sh
git shortlog -sne
```

No separate contributor list is maintained; git history is the record.
